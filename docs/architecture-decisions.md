# Architecture decisions

These decisions cover the WordPress migration from an Azure VM Scale Set to AKS. The [architecture diagram](architecture.md) shows how the components connect. The [operator runbook](operator-runbook.md) covers release verification, rollback, and teardown.

| Decision | Reason | Trade-off or limitation |
| --- | --- | --- |
| Manage the project infrastructure with Terraform and keep state in Azure Blob Storage. | The VMSS baseline and later infrastructure changes can be planned and reproduced from version-controlled configuration. Remote state gives Terraform a shared record of managed resources. | The backend has its own lifecycle and must stay available until cleanup of the project infrastructure is complete. State access must be restricted. |
| Reuse the East US 2 AKS cluster and peer it with the West US 2 project VNet. | West US 2 had reached its regional vCPU quota during provisioning. The reused cluster could reach the existing private MySQL server through peering. | The deployment depends on cross-region networking and DNS. The benchmark did not isolate the latency attributable to the network path. |
| Keep the Application Gateway URL and private MySQL database during migration. | The browser entry point and WordPress database could stay in place while the gateway switched its backend from the VMSS to Traefik on AKS. | The gateway adds a routing and health-check dependency. Application rollback through Helm and gateway routing changes are separate operations. |
| Package the Kubernetes deployment with Helm. | The chart keeps workload and environment values together, and release history gives operators a revision to verify and restore. | A Helm rollback restores the release configuration. Database and file recovery have their own procedures. |
| Run two WordPress replicas with a shared Azure Files claim. | Both replicas can read uploaded content through the same ReadWriteMany volume. | The single-node lab demonstrates replica behavior and shared storage. A node outage can affect both replicas. |
| Mount Key Vault secrets through Secrets Store CSI and Microsoft Entra Workload ID. | The WordPress pod can retrieve database credentials using its workload identity, keeping those credentials out of the chart and repository. | Pod startup depends on the CSI mount, identity federation, and Key Vault access. |
| Build and scan the image in GitHub Actions, publish to ACR, and deploy by digest. | The pipeline uses Azure OIDC and deploys the same artifact it publishes. The digest lets operators verify the running release against the workflow output. | The release depends on Azure federation, registry permissions, and scan availability. The vulnerability gate covers High and Critical findings with fixes available. |
| Alert on Application Gateway `HealthyHostCount` for the AKS backend. | The metric detects a loss of healthy backends from the gateway's perspective and sends email through the Azure Monitor action group. | A healthy gateway probe covers its configured endpoint. Testing WordPress and uploaded content still requires a browser or HTTP check. |
